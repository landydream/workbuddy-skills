# 项目级 Skill 维护规范

## 目标

将后续任务中经过验证、可重复使用的 FairyGUI 经验保存在当前工作区，使新的 Harness 会话能够重新读取，同时避免技能文件被一次性业务细节污染。

## 内容分类

| 内容 | 保存位置 |
|---|---|
| 全项目必须遵守的稳定规则 | `AGENTS.md` |
| 可独立执行的操作流程 | `.agents/skills/<skill-name>/SKILL.md` |
| 属性原理、故障原因、长篇说明 | `.agents/skills/<skill-name>/references/*.md` |
| 经验证的最小 XML 案例 | `.agents/skills/<skill-name>/examples/*.xml` |
| 自动校验或重复处理工具 | `.agents/skills/<skill-name>/scripts/*` |
| 旧页面、完整案例和设计资源 | `skill-assets/historical-project/` |

## 值得沉淀的条件

满足任一条件即可考虑记录：

- 同类问题很可能再次出现。
- 问题经过两轮以上修正才解决。
- 发现 FairyGUI 编辑器或 XML 的特殊约束。
- 确认了可稳定复用的公共组件或参数模板。
- 形成了可重复执行的验证方法。
- 找到了容易复发的错误及明确根因。

## 不应进入通用 Skill 的内容

- 只适用于单个活动的业务文案。
- 没有方法论意义的单个节点坐标。
- 未经验证的猜测。
- 临时替代资源的绝对结论。
- 密钥、令牌、账号和其他敏感信息。
- 大量完整正式资源副本。

## 提炼格式

重要经验优先按以下结构记录：

1. **适用场景**：什么时候会遇到。
2. **问题现象**：可观察到什么错误。
3. **根本原因**：为什么发生。
4. **错误做法**：哪些处理会导致问题。
5. **正确做法**：稳定的步骤或公式。
6. **最小示例**：必要时添加 XML。
7. **验证方法**：如何证明修复有效。
8. **适用边界**：哪些情况不能套用。

## 更新流程

1. 先搜索现有 Skill 和 references，避免重复章节。
2. 区分通用规则与案例证据。
3. 把通用结论写入 Skill 或 reference，把具体页面证据保留在历史案例。
4. 若判断可以自动化，优先增加校验脚本，而不是只记录文字提醒。
5. 检查 Markdown 链接、相对路径、技能 frontmatter 和示例文件。
6. 在任务最终答复中列出所有新增或更新的技能文件。

## Skill 命名与 frontmatter

目录名和 `name` 使用小写 kebab-case，例如：

```yaml
---
name: fairygui-ui-page-builder
description: 一句话说明能力、适用对象和触发场景。
---
```

一个 Skill 只负责一个清晰能力。若新知识形成独立输入、流程和验收标准，应新建 Skill，而不是无限扩充现有页面构建 Skill。

## 版本管理建议

- 当前工作区 `.agents/skills/` 是项目技能的唯一主版本。
- 用户级 `C:\Users\EDY\.agents\skills\` 仅作为发布副本，不在两处分别编辑。
- 同步用户级技能前先检查项目版本，并在最终答复中说明同步目标。
- 根目录旧版 `SKILL.md` 和实践文档可作为兼容入口，但新内容应优先维护在 `.agents/skills/`。
