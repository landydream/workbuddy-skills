# 局域网 Web 应用并发安全与发布运维

所有结论均有实测数据支撑（压测样本 ≥8000 次），非推演。

## 1. 并发读写损坏文件：必须"读写成对"替换

单文件 JSON（2MB 量级）+ 多线程服务器 + 前端定时全量保存，是最容易翻车的组合。实测损坏率：

| 配置 | 坏数据比例 |
|---|---|
| 裸 `open('w')` 写 + 裸读 | **85.7%** |
| 只改写入（原子写）+ 裸读 | 3.19% |
| 原子写 + 原子读（重试） | **0.00%** |

根因：`open(path, 'w')` 先截断为 0 再写，期间任何读取都拿到半截文件（实测抓到 `size=0`、半截、缺尾部三种样本）。

**原子写**：写临时文件 → `os.replace(tmp, target)`。

**两个 Windows 特有坑**：

| 坑 | 现象 | 修法 |
|---|---|---|
| 只改写入没用 | 原子写后仍有坏数据 | **读也必须重试**——`os.replace` 对"正在 open+read 的读方"不提供时序保证 |
| `os.replace` 抛 `PermissionError [WinError 5]` | 读方持有句柄 | 写侧做退避重试（如 12 次），否则保存返回 500、用户以为存上了其实没有 |

**接入时最容易漏的是读侧**：规格常写"改 3 处"，实际排查发现 `/api/load` 里还有一处裸读——漏掉它坏数据率只能从 85.7% 降到 3.19%。审计时用 grep 把所有 `open(` 落点列全，读写逐一替换。

**失败语义保真**：替换 `/api/load` 的裸读后，读到 `None` 仍要 `raise`，不能返回 `success + null`——否则前端以为项目为空，下一次自动保存就把损坏/空文件覆盖回去。

## 2. 乐观锁防丢失更新（`_rev`）

后保存者全量覆盖前者是最严重的静默事故（A 的编辑被 B 抹掉，无任何提示）。

语义设计（服务端 `/api/save`）：

```
不带 _rev        ⇒ 放弃检测、直接放行（向后兼容旧客户端）
_rev == 磁盘 rev ⇒ 放行，写回 rev+1
_rev != 磁盘 rev ⇒ 409 + code='REV_CONFLICT' + currentRev
force=true       ⇒ 跳过比对（用户在弹窗选了"强制覆盖"）
```

**前端分流是关键设计**：自动保存有多个触发点（定时器 + 各交互），一律弹窗会变成骚扰 ⇒ **自动保存静默跳过 + 顶部红色警告条**（可点击处理），**手动保存才弹"加载最新 / 强制覆盖"二选一**。

**`_rev = 0` 是合法初值**：服务端用 `raw is not None`、前端用 `undefined` 判断，两处都不能用 truthy 兜底——`0` 是 falsy，truthy 判断会让初值失效。

## 3. 开发/服务双副本分离

局域网有人在线时，"改代码 + 跑回归"和"用户在编辑"互踩。一次性解法是物理分离：

```
<project>/          开发副本：改代码、跑回归、AI 审查（绑定 127.0.0.1）
<project>-runtime/  服务副本：局域网用户访问，只有发布脚本能改（绑定 0.0.0.0）
```

发布唯一入口是一个 `publish.py` 脚本，铁律：

- **永不推活数据目录**（如 `data/`）与用户上传资源（如 `assets/images/`）；活数据只在 `--init` 建副本时拷一次。
- 验证脚本统一读环境变量取 base URL，**不得硬编码端口**。
- 备份逻辑不要放在"服务在跑"分支里——服务停机时活数据同样需要备份。

## 4. 发布加固四件套

| 件 | 做法 |
|---|---|
| TCP 探活 | 发 TCP 不发 HTTP，避免探活请求落进业务日志 |
| 在线检测 | `netstat` 查非本机远端 IP 的连接 |
| 自动备份 | 发布前备份 `data/`、用户资源到带时间戳的 `.backups/` |
| 代码/数据生效差异阻断 | 前端静态文件是请求时读盘（发布即生效），服务端代码是进程启动时加载（**必须重启**）。改动命中服务端代码**且有人在线 → 阻断发布**（`--force` 绕过）；只改静态文件 → 仅警告 |

另外提供 `--rollback`（只恢复数据不回滚代码）、`--dry-run`、`--strict`（需重启时非零退出）。

## 5. "有人在线"的正确判据

`ESTABLISHED` 连接数为 0 **不代表没人在线**——HTTP 短连接，用户开着页面空闲时连接已关闭，只剩 TIME_WAIT。正确做法：

```bash
# 隔 25 秒采两次
netstat -ano | grep <port> | grep TIME_WAIT
# 有新增源端口 ⇒ 有人还开着（前端自动保存会持续产生新连接）
```

同理，双进程时 localhost 与局域网可能绑到不同 PID（更具体的 bind 优先），改服务端代码前先 `netstat -ano | grep <port>` 确认监听进程，避免"补丁只加载进了一个进程"的双写隐患。

## 6. 回归测试会污染活数据：跑前必备份

回归脚本会写真实数据，且 data guard 恢复失败时残留能静默留存（文件仍是合法 JSON，不报错但内容丢了）。硬流程：

```
跑回归前: cp data/project.json .workbuddy/pre-regression-backup/project.json.<n>
跑完后  : 比对 → 有差就从这份恢复
```

**连带坑**：guard 恢复失败会在临时目录留 `active.lock`，此后所有验证/回归都会 abort。处理顺序 = 先用备份核验数据已恢复，再删 `active.lock` 和对应快照目录（**别用污染发生时打的快照恢复**）。

**恢复失败的根因**：guard 恢复后再哈希比对，在线用户的自动保存一直在写 ⇒ 哈希永远对不上 ⇒ 判定失败 ⇒ 残留留存。所以跑回归前还要先确认无人在线（见第 5 节）。

## 7. 其他实测教训

- **project.json 是运行时数据不是源码**：编辑器开着就被持续写入（实测静置 56 秒 +46 万字节）。变更基线必须排除它，否则 diff 每次误报，机制三天内被无视。
- **多写者隔离**：进程（如 watcher 脚本）会在人手修改后短时间内改文件，基线工具要支持会话参数隔离。
- **服务端日志可能是块缓冲**，不能用作实时探测器。
- **启动守卫**：服务器加 `_port_in_use()` 检查拒绝第二个实例，防止双实例双写。
